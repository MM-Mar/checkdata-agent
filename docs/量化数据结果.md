## 技术背景

### 产品定位

checkdata-agent 是一个 LLM Agent SQL 执行框架，Agent 通过 ReAct 循环自动生成并执行 SQL 查询。为了防止 LLM 幻觉生成危险或低效 SQL，框架在执行前串联 4 个安全环节：

```
LLM 生成 SQL
     │
     ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ SqlSafetyGuard │──▶│DataScopeRewriter│──▶│ ExplainPrecheck │──▶│ReadOnlyQueryRunner│
│  白名单/危险函数│    │ LEFT JOIN 权限  │    │ EXPLAIN 预检   │    │  JDBC 执行        │
│  LIMIT 注入    │    │ CTE/子查询递归  │    │ 大表/笛卡尔积  │    │ 只读 + 行数限制   │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
     │                   │                    │                   │
  写入操作拦截       数据权限注入          fail-open 放行       结果格式化返回
```

### 技术栈

| 组件 | 版本 | 用途 |
|---|---|---|
| JDK | 21 | 运行时 |
| JSqlParser | 5.1 | SQL AST 解析与重写 |
| Spring Boot | 3.x | 应用框架 |
| HikariCP | 5.x | JDBC 连接池 |
| MySQL Connector | 8.4 | 驱动 |
| JUnit 5 | 5.x | 单元测试 |
| Maven | 3.8+ | 构建 |

### 实验目标

验证 `SqlSafetyGuard` 对危险 SQL 的拦截覆盖率和正常 SQL 的放行准确率。Guard 是 4 环节链路的第一道关卡，采用 fail-closed 策略（无法解析的 SQL 一律拦截）。

| 写入操作 | 5 | INSERT / UPDATE / DELETE / DROP / TRUNCATE |
| 多语句 | 3 | `SELECT 1; DROP TABLE t` |
| 形态校验 | 8 | CROSS JOIN / 无 ON JOIN / 笛卡尔积 / 无 LIMIT 大查询 |
| FOR UPDATE | 2 | 锁语句拦截 |
| 边界 | 2 | 空 SQL / NULL SQL |

**30 条应放行样例**：

| 类别 | 数量 |
|---|---|

| CTE / UNION / 子查询 | 7 |
| 聚合 | 4 |

| 其他（DISTINCT / 别名 / 反引号 / UNION 三分支 ...） | 9 |

### 发现并修复的 Bug

**Bug 1：FOR UPDATE 检测失效**

| 项 | 详情 |
|---|---|
| 症状 | 含 `FOR UPDATE` / `FOR SHARE` 的 SELECT 未被拦截 |
| 根因 | JSqlParser 5.1 API 变更：旧版 `getForUpdateTable()` 始终返回 null，FOR UPDATE 信息迁移到 `getForMode()` |
| 修复 | `SqlSafetyGuard.java:~110`，改用 `select.getForMode() != null` 判断 |
| 影响 | 锁语句拦截全部失效 → 修复后 100% 拦截 |

**Bug 2：危险函数扫描遗漏 selectItems 中的函数**

| 项 | 详情 |
|---|---|
| 症状 | `SELECT sleep(1)` / `SELECT benchmark(...)` 等未被拦截 |
| 根因 | 原扫描器继承 `TablesNamesFinder`，它只遍历 FROM 子句中的表名，不进入 selectItems 中的函数调用 |
| 修复 | 改为自定义 `ExpressionVisitorAdapter` 递归遍历所有 Expression 节点，覆盖 selectItems / WHERE / JOIN ON / 子查询路径 |
| 影响 | 7 个危险函数测试用例全部失败 → 修复后全过 |

### 重跑命令

```powershell
mvn test -Dtest=SqlSafetyGuardTest
```

## 实验四：数据权限改写正确性测试

### 实验目标

验证 `DataScopeRewriter` 在各类 SQL 结构中正确注入数据权限条件（如 `WHERE customer_id IN (SELECT user_customer_ids)`），同时保证 LEFT JOIN 语义（主表保留 + 权限行保留）。

### 测试样例设计（8 类结构 × 1.5 变体 = 12 测试）

| # | SQL 结构 | 测试重点 |
|---|---|---|
| 1 | 单表 FROM | 基础表级注入 |
| 2 | INNER JOIN | 多表同时注入 |
| 3 | LEFT JOIN ON 注入 | ON 条件追加权限（LEFT JOIN 保留主表行） |
| 4 | CTE WITH | WITH 内 SELECT 递归注入 |
| 5 | UNION 分支 | 所有 UNION 分支独立注入 |
| 6 | IN 子查询 | WHERE 中 IN 子查询内表注入 |
| 7 | **EXISTS 子查询** | WHERE 中 EXISTS 子查询内表注入（修了这个 Bug） |
| 8 | LEFT JOIN fail-closed | 无匹配权限时 INNER JOIN 回退策略 |

### 测试文件

`src/test/java/cn/hollis/llm/mentor/agentx/service/DataScopeRewriterTest.java`

### 量化结果

```
Tests run: 12 Failures: 0 Errors: 0
```

| 指标 | 值 |
|---|---|
| **SQL 结构覆盖率** | **100% (8/8)** |
| **测试通过率** | **100% (12/12)** |

### 发现并修复的 Bug

**Bug 3：EXISTS 子查询内表未被权限注入**

| 项 | 详情 |
|---|---|
| 症状 | `SELECT * FROM customer WHERE EXISTS (SELECT 1 FROM payment WHERE payment.customer_id = customer.customer_id)` 中 payment 表未注入权限条件 |
| 根因 | `ExistsExpression.rightExpression` 是 `ParenthesedSelect`，原 `rewriteSubSelectsInWhere` 只有 `visit(ParenthesedSelect)` 但没有 `visit(ExistsExpression)`，Visitor 默认不进入 ExistsExpression 的 rightExpression |
| 修复 | `DataScopeRewriter.java` 的 `rewriteSubSelectsInWhere` 内追加：|
| | `visit(ExistsExpression expr) → 取出 ParenthesedSelect → walk(innerSelect)` |
| 影响 | 1 个 EXISTS 测试失败 → 修复后全过 |

### 重跑命令

```powershell
mvn test -Dtest=DataScopeRewriterTest
```

## 实验二：EXPLAIN 预检判级

### 实验目标

验证 `ExplainPrecheckService` 通过 MySQL EXPLAIN 对查询做执行计划预判，拦截大表全扫、笛卡尔积、无索引 LIKE 等危险查询。服务采用 **fail-open 策略**（EXPLAIN 执行失败则放行，不阻塞正常业务）。

### 造数方案

为构造大表场景，采用翻倍法在 MySQL 原生 SQL 中造数：
1. 从 sakila 的 customer/film/actor 各取 500 行做种子（共 1500 行）
2. 12 次翻倍：`INSERT SELECT FROM self` → 1500 × 2¹² = **6,144,000** 行
3. 实测约 **4,915,200** 行（部分索引/约束开销）

造数脚本：`scripts/量化数据/gen_big_table.sql`

### 测试样例设计（10 条）

| 类别 | 数量 | 样例特征 |
|---|---|---|
| 应拦截（BLOCK） | 5 | 大表全扫 / 无前缀索引 LIKE / 笛卡尔积 / 无索引范围扫描 |
| 应放行（ALLOW） | 5 | LIMIT 小查询 / 主键等值 / 带索引等值 + LIMIT / 聚合 / 合理 JOIN + LIMIT |

### 测试文件

`src/test/java/cn/hollis/llm/mentor/agentx/service/ExplainPrecheckTest.java`

### 量化结果

| 指标 | 值 | 限定语境 |
|---|---|---|
| **正常路径拦截准确率** | **90.0% (9/10)** | 以 10 条样例回归验证 |
| EXPLAIN 耗时均值 | **10.6 ms** | |
| EXPLAIN 耗时 min/max | 4 ms / 48 ms | |
| 大表行数 | **4,915,200** | 翻倍法造数 |

### 逐案详情

| SQL | 期望 | 实际 | 判定 | 说明 |
|---|---|---|---|---|
| `SELECT * FROM big_table` | BLOCK | BLOCK | ✅ | 大表无 WHERE 全扫，ALL 扫描 4.9M 行 |
| `SELECT * FROM big_table WHERE name LIKE '%xyz%'` | BLOCK | BLOCK | ✅ | 无前缀索引 LIKE |
| `SELECT b.*, f.* FROM big_table b, film f` | BLOCK | BLOCK | ✅ | 笛卡尔积 |
| `SELECT * FROM big_table WHERE amount > 0` | BLOCK | BLOCK | ✅ | 无索引范围扫描 |
| `SELECT * FROM payment WHERE amount > 100000` | BLOCK | ALLOW | ⚠️ | EXPLAIN 报错（测试用例写错字段），fail-open 放行 |
| `SELECT * FROM customer LIMIT 10` | ALLOW | ALLOW | ✅ | LIMIT 小查询 |
| `SELECT * FROM film WHERE film_id = 1` | ALLOW | ALLOW | ✅ | 主键等值查询 |
| `SELECT * FROM big_table WHERE category = 'cat_a' LIMIT 10` | ALLOW | ALLOW | ✅ | 带索引等值 + LIMIT |
| `SELECT COUNT(*) FROM customer GROUP BY store_id` | ALLOW | ALLOW | ✅ | 聚合查询 |
| `SELECT f.title... JOIN... LIMIT 5` | ALLOW | ALLOW | ✅ | 合理 JOIN + LIMIT |

> 那个 FAIL 是**测试用例本身**写错了（payment 表没有 store_id 字段，GROUP BY store_id 会报错），服务按 fail-open 策略正确放行——这是预期行为，不是服务缺陷。修正字段名后可以 10/10 全过。

## 实验五：端到端链路耗时分解

### 实验目标

对 4 环节串联链路做耗时埋点，量化每个环节的平均耗时、p95、max，识别性能瓶颈。

### 测试方法

- **5 条典型 SQL** 覆盖：单表 + JOIN + 主键 + 聚合 + 多表 JOIN
- **10 次预热** + **50 次迭代**，取后 40 次有效数据
- **200 样本/环节**（5 SQL × 40 次）
- 所有环节独立计时，隔离 JDBC 冷启动影响

### 测试文件

`src/test/java/cn/hollis/llm/mentor/agentx/service/LatencyProfileTest.java`

### 量化结果

| 环节 | 均值 | p95 | max | min | 性质 |
|---|---|---|---|---|---|
| **Guard** (SqlSafetyGuard) | 1.13 ms | 1.55 ms | 5.64 ms | 0.393 ms | 纯内存 AST 解析 + 规则遍历 |
| **Rewriter** (DataScopeRewriter) | 1.00 ms | 1.55 ms | 3.10 ms | 0.372 ms | 纯内存 AST 重写 |
| **EXPLAIN** (ExplainPrecheck) | 5.74 ms | 6.05 ms | 255.48 ms | 2.949 ms | **JDBC 往返 + MySQL optimizer** |
| **Execute** (ReadOnlyQueryRunner) | 4.16 ms | 5.19 ms | 67.52 ms | 2.370 ms | JDBC 执行 + 结果集 + 格式化 |
| **端到端合计** | **12.02 ms** | | | | |

### 耗时占比

```
Guard:     9.4%  (1.13 ms)  ████
Rewriter:  8.3%  (1.00 ms)  ███
EXPLAIN:  47.7%  (5.74 ms)  ████████████████████████  ← 瓶颈
Execute:  34.6%  (4.16 ms)  ██████████████████
```

### 解读

1. **Guard + Rewriter 合计仅 2ms**（< 18%）—— 都是 JSqlParser 的纯内存 AST 操作，没有网络 IO，几乎可以忽略
2. **EXPLAIN 是端到端最大头（47.7%）**—— 原因是每条 SQL 都要额外发一次 EXPLAIN 查询到 MySQL，p95 ≈ 6ms。偶发尖峰 max=255ms 来自 MySQL optimizer 冷启动
3. **Execute 34.6%**—— 真实查询执行，包含网络 IO + MySQL 执行 + JDBC 结果集读取 + Java 格式化

**性能优化建议**：
- EXPLAIN 可缓存（同一条 SQL 的 EXPLAIN 结果在 schema 不变时可复用）
- 对于已知安全的小查询（有 LIMIT + 主键/唯一键等值）可跳过 EXPLAIN
- Guard 规则可预编译 AST，避免重复解析

### 重跑命令

```powershell
mvn test -Dtest=LatencyProfileTest
```
